# Accept a Milestone

An **acceptance run** is one clean-room, end-to-end pass that answers a single question in plain language: *is this milestone done?* You drive every step and write the **verdict**, so the person accepting the milestone needs no prior knowledge of the system.

Work with **fresh eyes**: assume nothing about the running system or your own memory of it. Everything you claim must come from either (a) a newcomer-readable source — the milestone's spec, acceptance criteria, README, changelog — or (b) output you just observed. If a step needs insider knowledge a newcomer wouldn't have, that gap is a finding to report, not something to fill from assumption. This is what makes the run safe for someone who has never touched the system: if *you* need no insider knowledge, neither do they.

The run is a **clean room**: it starts by destroying leftover state and ends the same way, so the result is identical whether this is the first run or the fifth. A milestone that can't be brought up from nothing, or can't be torn down cleanly, fails acceptance — those are acceptance criteria, not chores.

## Ground rules

- **Observe, don't assume.** Every pass/fail cites output you saw. "Should work" is not a result.
- **One scenario at a time.** Run it, observe it, record its result, then move on. No batching.
- **A blocked step is a finding.** If you can't run something, record it `BLOCKED` with the reason and keep going — never silently skip it.
- **Plain language in the verdict.** No jargon, no internal names without a one-line gloss. Write for someone who has never seen this system, in the reader's own language.

## Scope the run

Establish two things before touching the system:

1. **What "done" means** — the milestone's acceptance criteria. Find them in its spec/PRD/issue, `CHANGELOG`, or release notes; list each as a checkable scenario. If none are written down, derive them from the milestone's stated features and show the list — this list is what you accept against.
2. **The lifecycle commands** for *this* system — how to tear down, bring up, and destroy it (install / build / migrate / seed / start / stop). If an `ACCEPTANCE.md` sits at the project root, use its commands and scenarios verbatim. Otherwise derive them from the README, scripts, and CI config.

Completion: a written run plan listing every acceptance scenario plus the exact commands for teardown, init, and destroy. If you derived it fresh, offer to save it as `ACCEPTANCE.md` so future runs replay deterministically.

## Teardown

Bring the environment to a known-clean slate *before* building anything: stop running instances, drop test databases and volumes, clear caches and artifacts generated by prior runs.

Completion: the state that init will create does not yet exist — confirmed by observing its absence (no stale process, no leftover DB/volume), not by assuming.

## Precheck

Verify every prerequisite the run needs: required tools and versions, environment variables, credentials, and reachability of external services. Check them; don't trust them.

Completion: every prerequisite checked and reported present — or the run stops here with a plain-language list of what's missing and how to obtain it, one a newcomer could resolve without asking you.

## Init

Bring the system up from nothing, following the lifecycle commands in order: install, build, migrate, seed, start. This is itself an acceptance scenario — a clean bring-up that fails is a milestone failure.

Completion: the system reports healthy (health check passes, expected services listening, or smoke ping succeeds), with the evidence quoted.

## Step test

Run each acceptance scenario from the run plan, one at a time. For each: state in one line what you are verifying, run it, observe the actual result, and record `PASS` / `FAIL` / `BLOCKED` with the evidence you saw.

Completion: every scenario in the run plan has a recorded result with cited evidence — every criterion accounted for, none left unaddressed (not "most tested").

## Destroy

Tear the environment down again with the destroy commands, returning to the same clean slate teardown produced.

Completion: the system and its state are gone, confirmed by observation. A failed or messy teardown is recorded `FAIL`, because repeatable teardown is an acceptance criterion.

## Verdict

Write the acceptance report for the person signing off:

- **Result** — one word: ACCEPTED (every scenario passed) or REJECTED (anything failed or blocked).
- **Scenario table** — each acceptance criterion, its PASS/FAIL/BLOCKED, and one line of evidence.
- **What failed and why** — for anything not passing, the plain-language cause and, if known, the fix.
- **How to reproduce** — the single command or short sequence that re-runs this acceptance.

Completion: a report a non-expert can read top to bottom and decide accept-or-reject without asking a question.
